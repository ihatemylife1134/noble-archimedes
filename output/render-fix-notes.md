# Render-fix investigation notes (2026-09-25)

Rendering is **not yet verified**. DMA completions now reach the guest ring and GS VRAM has nonzero pages, but captured display pixels remain black. Keep candidate binaries and logs separate from the original executable.

## Confirmed defects and changes

- The guest DMA completion ring has 11 slots. In `output/diag_startup_trace/candidate.stderr.log`, completion causes 2 and 1 were queued at slots 0 and 1, then repeated genuine cause-10 VBlank callbacks wrapped the ring before DMA worker thread 3 consumed it. The worker read cause 10 and did not recycle DMA nodes; the free list emptied, leaving the frame blank. The runtime scheduler previously favored pending callbacks over a ready worker. The scheduler owner is testing fair callback/thread dispatch in `tools/PS2Recomp/ps2xRuntime/src/lib/Kernel/EeScheduler.cpp`, with `ee_dispatch_policy_test.cpp`.
- The runtime assigned an asynchronous callback stack at `0x1FFFFF0`, overlapping the guest main thread stack declared as base `0x1FF0000`, size `0x10000`. The callback saved RA over the main thread's saved RA at `0x1FFFFD8`, causing an intermittent `pc=0` exit at guest `0x40FB44`. Runtime callback stack allocation now starts below `0x1FE0000`; `ee_async_stack_test.cpp` contains a collision regression. The guest declared stack bound leaves 64 KiB of separation.
- A generated registration table had an inclusive empty sentinel at index 1,355,112, exactly one past the 1,355,112-element table. `src/recomp/generated/register_functions.cpp` omits the sentinel; `tools/optimize_register_functions.py` validates parsed ranges, with `tools/tests/test_optimize_register_functions.py`. This is a real out-of-bounds write, but it is **not established as the rendering cause**.
- The scheduler subsequently exposed an incomplete lifecycle for negative-ID callback dispatchers: a reschedule after a callback function return could clear `m_currentThreadId` without requeuing or completing the dispatcher. It then retained `Running` status and could not be reused, eventually exhausting callback stacks. The scheduler owner is fixing this and adding `ee_dispatcher_lifecycle_test.cpp`. Both PC=0 completion and nonzero-PC yield need coverage.

## Checkpoint 2026-09-27: garbled menu fixed (VIF1 DIRECT image continuation)

Root cause: after a VIF1 `DIRECT` whose GIF payload ends with an IMAGE tag, `PS2Memory::processVIF1Data` stopped decoding VIFcodes and fed the following bytes to GS PATH2 as pixels. The game uploads every texture/CLUT as `DIRECT 6` (BITBLTBUF/TRXPOS/TRXREG/TRXDIR + IMAGE tag) followed by a TTE REF tag whose upper half is `NOP; DIRECTHL n`, so those 8 VIFcode bytes were written into VRAM and every upload was shifted by 8 bytes (palette raster at DBP 7168 began `00000000 51000040`; 32 KiB textures began `NOP; DIRECTHL 0x800`). Evidence: texture bytes in the late dump match VRAM exactly at an 8-byte offset; all swizzle tables match PCSX2 `GSTables.cpp` byte-for-byte.

Fix (`ps2xRuntime/src/lib/ps2_vif1_interpreter.cpp`, `include/runtime/ps2_memory.h`, `src/lib/ps2_memory.cpp`): VIFcodes are always decoded; a pending IMAGE continues through the next DIRECT/DIRECTHL payload (`submitVif1DirectPayload`), and a DIRECT payload cut off at the end of a transfer continues raw via `m_vif1DirectRemainingQwc`. Regression `ps2xRuntime/tests/vif1_direct_image_continuation_test.cpp` failed red (pixel 0 = NOP) and passes green. Two `ps2x_tests` cases that asserted the non-hardware raw-continuation behaviour were rewritten to send the image through a following DIRECT/DIRECTHL. `ps2x_tests`: 437 run, 432 pass, 5 pre-existing scheduler/RPC failures, none new.
